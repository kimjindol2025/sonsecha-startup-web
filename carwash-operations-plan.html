LEGAL & COMPLIANCE

물환경보전법 제38조의2와 세차장 폐수 리스크

세차장은 단순 상가가 아닌 '폐수배출시설'입니다. 행정처분 및 과태료 위험을 사전에 방어해야 합니다.

🚨 법적 핵심 주의사항: '폐수배출시설 및 수질오염방지시설 운영기록부' 미보관 시 처벌

물환경보전법에 따라 세차장 사업자는 폐수처리시설의 일일 가동 상태, 약품 투입량, 슬러지 발생·위탁량을 매일 기록하고 3년간 사업장에 보관해야 합니다. 위탁 관리업체에 청소를 맡기더라도 최종 법적 책임은 대표자(점주)에게 있으며, 미작성·허위작성 적발 시 300만 원 이하의 과태료 및 조업정지 처분을 받게 됩니다.

본 통합 운영관리 시스템은 일일 계량기 수치 입력만으로 환경부 고시 서식에 맞춘 3년 보관용 일지를 자동 영구 보존합니다.

DATA ARCHITECTURE

통합 데이터 스키마 구상 (TypeScript 예시)

기존의 5개 개별 LocalStorage 저장 구조를 일원화하여, 하루 1개의 완결된 레코드로 관리하는 정규화 스키마입니다. 

// sonsecha-app-unified-ops-v1 스키마 정의
export interface DailyOperationClosing {
  id: string; // "YYYY-MM-DD"
  date: string;
  weather: 'sunny' | 'cloudy' | 'rain' | 'snow';
  manager: string; // 마감 근무자

  // 1. 매출 & 결제
  sales: {
    totalRevenue: number;     // 순매출
    totalCars: number;        // 방문 차량수
    averageTicket: number;    // 평균 객단가 (totalRevenue / totalCars)
    courseCounts: {
      basic: number;
      underbody: number;
      bubble: number;
      premium: number;
    };
    channelBreakdown: {
      kioskCard: number;
      rfCardReload: number;
      cash: number;
      mobileApp: number;
    };
    refunds: number;
  };

  // 2. 장비 & AS
  equipment: {
    downtimeMinutes: number; // 전체 가동 정지 시간(분)
    bayStatus: { [bayId: string]: 'normal' | 'caution' | 'offline' };
    issues: Array<{
      equipmentName: string;
      symptom: string;
      status: 'reported' | 'in_repair' | 'resolved';
      cost?: number;
    }>;
  };

  // 3. 환경 & 폐수 (물환경보전법 제38조의2 준수)
  compliance: {
    waterMeterStart: number;
    waterMeterEnd: number;
    waterUsageM3: number;        // 일일 용수 사용량 (㎥)
    powerMeterKwh: number;       // 방지시설 전력 적산계
    wastewaterTreatedL: number;  // 폐수 정화 처리량 (L)
    sludgeHandledKg: number;     // 슬러지 인출량 (kg)
    chemicalAddedKg: number;     // 약품 투입량
    oilSeparatorCleaned: boolean;// 유수분리조 청소 여부
    status: 'normal' | 'caution' | 'action_required';
  };

  // 4. 소모품 & 재고
  inventory: {
    chemicalUsageAlerts: string[]; // "스노우폼 부족", "발수제 발주 필요"
    replenishedItems: Array<{ item: string; quantity: number }>;
  };

  // 5. 고객 & 민원
  incidents: {
    complaintCount: number;
    records: Array<{
      carNumber: string;
      issueType: 'scratch' | 'wash_quality' | 'payment_error' | 'facility';
      summary: string;
      resolved: boolean;
    }>;
  };

  createdAt: string;
  updatedAt: string;
}

  • 다점포(본사-가맹점) 프랜차이즈 통합 관제 대시보드
MVP IMPLEMENTATION SPEC · v1.1

코덱스 작업 지시 · 1호점 일일 마감

1단계 구현은 이 절의 계약을 따른다. 위 화면과 TypeScript 예시는 제품 구상이다. 첫 사용자는 대한이엔지 테스트 매장의 마감 담당자다. 합성 데이터로 먼저 검증한다.

목표

한 매장의 담당자가 영업일별 마감을 저장하고, 새로고침 뒤 재조회·정정할 수 있게 한다. 기존 운영 앱에서 같은 날짜의 자료를 불러오고, 매출·장비·폐수·재고·민원 요약을 마감 스냅샷으로 남긴다. 최초 마감 목표 시간은 5분이며, 실제 담당자 1회 측정값을 기록한다.

작업 범위와 변경 파일

  1. daily-closing-app.html을 추가한다. vite.config.js의 다중 페이지 입력에 등록하고 operations-apps.html의 실제 메뉴 렌더링 위치와 이 기획서에서 상대 링크로 연결한다. operations-apps.html의 메뉴는 src/operations-apps.js에서 렌더링되는지 먼저 확인한다.
  2. src/daily-closing.js에 화면과 저장 흐름을, src/daily-closing-domain.js에 검증·가져오기·집계를 구현한다. 기존 Vite 빌드와 CSS를 재사용한다. 새 런타임 의존성, TypeScript, 서버, DB 도입은 후속 범위다.
  3. 기존 5개 앱의 원본 키와 화면 동작을 보존한다. 자동 AS 발행, 재고 차감·발주, 실결제, 외부 전송, 사진·차량번호 저장, 직원 계정, 다점포, 법정 출력은 후속 단계로 둔다. 환경 입력은 내부 참고 기록으로 표시하며 법정 적합성과 장기 보관은 관할·서식 확인을 별도 게이트로 둔다.

화면과 사용자 흐름

  1. 상단에서 영업일을 고른다. 최초 기본값은 Asia/Seoul의 오늘이다. 이미 저장된 날짜는 읽기 모드에서 열고 정정으로 편집한다. 미저장 편집 상태에서 날짜를 바꾸면 폐기 확인을 받는다.
  2. 기존 기록 불러오기로 선택일 자료를 미리 본다. 적용 전 출처별 건수와 누락·충돌을 보여준다. 불러오기는 편집 중인 메모나 입력을 덮을 때 확인을 받으며, 마감 저장 전까지 브라우저 저장소에 기록하지 않는다.
  3. 5개 입력 묶음은 기본·매출, 장비, 폐수, 재고, 민원·인수인계다. 저장 전 화면에 순매출·객단가, 장비 조치, 재고 부족, 환경 기록 여부를 보여준다. 저장 실패 시 편집 내용을 보존하고 오류 위치를 표시한다.
  4. 저장 성공 후 읽기 모드로 전환하고 마감 시각과 개정번호를 표시한다. 정정에는 변경 사유를 요구하고 직전 버전을 이력에서 조회할 수 있게 한다.

데이터 계약

sonsecha-app-unified-ops-v1에 JSON 객체 하나를 저장한다. 최상위 필드는 schemaVersion: 1, records다. records[date]에는 개정판 배열을 저장하며 마지막 항목이 현재본이다. 개정판 공통 필드는 revision(1부터 증가), savedAt(UTC ISO 시각), reason(첫 저장은 null, 정정은 1~300자), 아래 입력 객체다. 영업일은 실제 달력의 YYYY-MM-DD이며 미래일은 막는다. 필수 문자열은 공백 제거 후 검사하고 메모는 500자 이하로 제한한다. 숫자 빈칸은 0과 구별한다.

  • 기본 manager 1~60자 필수, weather는 맑음·흐림·비·눈·기타 또는 null.
  • 매출 grossKrw, refundKrw, cars는 0 이상 안전 정수 필수. rfReloadKrw는 별도 참고 금액이며 미입력은 null. 순매출 = 매출 − 환불. 당일 이전 판매 건의 환불을 기록할 수 있도록 음수 순매출을 허용한다. 객단가는 차량 0대면 null, 나머지는 순매출 ÷ 차량 수를 원 단위로 반올림한다. RF 충전액은 순매출과 객단가에서 제외한다.
  • 장비 equipment[]는 name, status(정상·예방정비·수리필요·AS요청), downtimeMinutes(0 이상 정수 또는 null), note로 구성한다. 수리필요·AS요청 행에 메모 필수. 위젯은 장비 조치 행 수를 표시한다.
  • 폐수 wastewater는 null 또는 waterStartM3, waterEndM3, treatedL, sludgeKg, note를 포함한다. 계량기 두 값은 함께 입력하고 종료 ≥ 시작을 검사한다. ㎥는 소수 셋째 자리까지 받고 1,000배한 정수로 차감한 뒤 ㎥로 표시한다. 처리량은 정수 L, 슬러지는 소수 첫째 자리 kg까지 허용한다. 각 수치는 0 이상이며 부분 입력은 화면에 ‘부분 기록’으로 표시한다.
  • 재고 inventory[]는 item, currentStock, minimumStock을 저장한다. 수량은 0 이상, 소수 첫째 자리까지 허용한다. 현재 ≤ 최소이면 부족으로 표시한다. 입력에서 품목 이름의 앞뒤 공백을 제거하고 중복 품목은 저장 전에 해결하도록 표시한다.
  • 민원·인수인계 complaintCount는 0 이상 정수 또는 null, handoverNote는 선택이다. 불러올 기록이 없는 장비와 재고는 빈 배열로 두고 화면에 ‘기록 없음’을 표시한다.

기존 자료 읽기 계약

src/operations-apps.js가 쓰는 sonsecha-app-{sales,equipment,wastewater,inventory,diary}-v1 배열에서 선택한 date와 정확히 일치하는 행만 읽는다. 원본 키에는 쓰기·삭제를 수행하지 않는다. 과거 버전의 숫자 문자열은 공백 제거 후 해당 필드 규칙을 충족할 때만 변환한다. 빈 문자열은 미입력, 손상 JSON·비배열·유효하지 않은 행은 출처와 건수를 표시하고 해당 출처의 자동 적용을 막는다.

  • 매출 기존 채널값만으로 RF 충전 포함 여부를 확정할 수 없다. sales, refunds, cars 원본 집계는 미리보기 참고용으로만 표시한다. 담당자가 충전액을 분리한 값을 마감에 직접 입력한다. 일지의 매출·차량수는 합산하지 않는다.
  • 장비·재고 장비는 equipment → name, downtime → downtimeMinutes, status/note를 반영한다. 재고는 item/currentStock/minimumStock을 반영한다. 같은 품목이 여러 건이면 후보를 모두 표시하고 담당자가 하나를 선택한다.
  • 폐수·일지 폐수 treated/sludge는 설비 간 중복 가능성이 있으므로 원본을 미리 보여주고 담당자가 확인한 총량을 입력한다. 계량기 값은 직접 입력한다. 일지 complaints/weather/note는 미리보기 후보로 제공하고 여러 건이면 담당자가 선택한다.

저장·동시성·실패 처리

같은 브라우저 프로필·같은 오리진의 단일 매장용이다. 마감 키 이름의 Web Lock 안에서 원본을 다시 읽고 현재 개정번호를 편집 시작 시 번호와 비교한다. 다르면 충돌을 표시하고 재조회하도록 한다. 신규 저장은 번호 0을 기준으로 비교한다. 저장 버튼을 처리 중 비활성화하고 저장은 새 JSON 한 번 쓰기로 완료한다. 저장 용량 초과, 차단, 잠금 미지원, 손상 JSON, 알 수 없는 버전에는 쓰기를 중단하고 기존 원문과 화면 입력을 보존한다. 사용자 입력은 텍스트로 출력한다. 마감 기록 조회 화면에서 JSON 백업을 내려받을 수 있게 하며 파일에는 schemaVersion과 개정 이력을 포함한다. 자동 복원과 오리진 간 이전은 별도 범위로 표시한다.

검증과 완료 조건

  1. 정상 계산 기준값. 매출 100,000원·환불 10,000원·차량 9대·RF 충전 20,000원 → 순매출 90,000원·객단가 10,000원. 차량 0대 → 객단가 ‘—’. 계량 1420.500 → 1428.700 → 8.200㎥. 현재·최소 수량 2 → 부족.
  2. 실제 브라우저에서 메뉴 → 일일 마감 → 기존 자료 미리보기 → 저장 → 새로고침 → 같은 날짜 재조회 → 정정 순으로 검증한다. 신규 한 건·정정 한 건·기존 개정 보존·요약 일치와 JSON 백업을 확인한다. KST 자정 경계도 확인한다.
  3. 두 탭에서 같은 날짜를 열고 선행 저장 후 후행 저장을 시도해 충돌을 확인한다. 중복 클릭, 저장 실패, 손상 JSON, 미래일, 계량기 역전, 재고 중복, 스크립트 문자열 입력을 시험한다. 기존 5개 키 원문이 동일한지 비교하고 기존 앱의 조회·저장을 별도 합성 데이터에서 확인한다.
  4. npm run build 및 GITHUB_ACTIONS=true npm run build를 수행한다. 두 번째 빌드는 프로젝트 하위 경로로 제공해 마감 URL·메뉴 링크·CSS·모듈 로드와 모바일 390px 화면을 확인한다.
  5. 구현 변경 파일, 테스트 환경, 입력·기대값·실제값, 브라우저 캡처, 담당자 소요 시간, 독립 검증 결과를 제출한다. 모든 필수 검증이 통과해야 PASS다. 환경이나 기능이 막히면 최초 실패 지점과 재현 절차를 적고 BLOCKED로 판정한다.
