# 로그인 제외 창업 진행판 구현

2026년 11월 7일 한국시간. Kim의 “코딩 시작 로그인은 이번에는 패스”에 따라, 사업·후보지 등록부터 검토 의뢰·답변·재문의까지 로컬 개발본을 구현했어요. 로그인·본인 확인·실제 직원 계정은 연결하지 않았어요. 시험 신원으로 자료 소유·배정 권한을 검증하며 실제 고객 접수용으로 배포한 상태는 아니에요.

작업 사본은 `/home/kim/workbench/sonsecha-prd-v3`, 브랜치는 `feat/prd-v3-review-workspace`예요. 기존 서비스 폴더의 미커밋 수정과 운영 자료를 그대로 보존하기 위해 별도 worktree를 사용했어요. 원본 소스 해시와 변경 파일은 `implementation-results.json`, 준비 당시 기준선은 `baseline.json`에서 확인할 수 있어요.

## 확인할 수 있는 흐름

고객 가로 사업을 만들고 후보지 이름·주소·면적·가격·매물 주소·메모를 저장해요. 빈 값과 0은 구분하고, 후보지 변경 때 자료 버전을 추가해요. 의뢰는 제출 직전 확인한 후보지 버전을 보존하고 접수번호를 발급해요. 보류·탈락 후보지도 삭제하지 않아요.

관리 책임자는 사업을 담당자에게 배정해요. 담당자는 현재 배정된 사업에서 수동 허가 항목·근거·확인 주체·확인일·재확인 사유를 기록하고 공개 답변·상태 변경·내부 메모를 작성해요. 고객은 공개 답변과 필요한 다음 행동을 확인하고 같은 접수에 재문의할 수 있어요. 답변 정정은 기존 답변에 연결한 새 기록으로 추가해요.

접수·메시지·답변·사진·배정에는 제출 식별값을 적용했어요. 응답을 받지 못해 같은 내용을 재전송해도 중복으로 저장하지 않아요. 오래된 자료 버전과 식별값 내용 충돌은 덮어쓰지 않고 안내해요. 저장 실패 때 폼과 사진 선택은 유지하고, 버전 충돌은 최신 자료를 확인한 뒤 사용자가 재시도를 결정해요. 저장된 뒤 목록 조회만 실패한 경우도 저장 실패와 구분해요.

사진은 PNG·JPEG·WebP 형식과 헤더를 확인하며 한 장 2MB, 접수당 10장으로 제한해요. 원본 파일은 공개 정적 폴더에 두지 않고 매번 현재 자료 권한을 검사해 내려받게 해요. 고객에게는 내부 메모·비공개 파일·배정 사유가 반환되지 않아요. 재배정이 확정되면 이전 담당자의 신규 조회·수정·파일 요청도 차단해요.

## 로컬 실행

현재 Node 환경과 설치된 의존성을 사용해요. 새 패키지나 외부 서비스는 추가하지 않았어요.

```bash
cd /home/kim/workbench/sonsecha-prd-v3
npm run build
NODE_ENV=development WORKSPACE_DEMO=1 WORKSPACE_DATA_DIR=/tmp/sonsecha-workspace-review WORKSPACE_PORT=40435 npm run workspace:preview
```

새 시험 서버를 직접 실행하는 명령이에요. 기존 PM2 서비스나 운영 서버를 재시작하는 명령이 아니에요. 사용하려는 포트가 이미 사용 중이면 다른 미사용 포트를 선택하세요. 새 서버는 `127.0.0.1`에만 바인딩하고 `/workspace.html`을 열어요. `WORKSPACE_PORT=0`이면 빈 포트를 자동으로 고르고 콘솔에 주소를 표시해요. 입력 자료는 지정한 시험 디렉터리의 `workspace.sqlite`에 저장돼요.

명시적으로 시험 실행을 켜지 않거나 `NODE_ENV=production`이면 서버 시작을 거부해요. 기존 상담·상품 데이터 파일이 있는 디렉터리도 사용할 수 없어요. 시험 역할 선택은 이 서버에만 있고 기존 `server.mjs`에는 추가하지 않았어요. 로그인 화면·인증번호 발송·비밀번호·외부 신원 검증은 만들지 않았어요.

시험 순서는 고객 가 → 사업·후보지 등록·의뢰 → 관리 책임자 → 담당자 가 배정 → 담당자 가 → 검토 중·항목 기록·공개 답변 → 고객 가 → 결과 확인·재문의예요. 고객 나와 담당자 나로 바꾸면 다른 사람의 자료가 보이지 않는지도 확인할 수 있어요.

## 검증과 증거

- `npm run build`: Vite 빌드와 정적 파일 패키징 통과. 기존 가이드·상품·관리자 자산도 함께 빌드했어요.
- `npm run test:workspace`: 20개 서버 시험 통과. 소유권 위조, 팀 범위, 미배정·재배정, 상태 전이, 공개·내부 분리, 파일 접근, 응답 유실 재시도, 동시 저장·원자적 복구를 확인했어요. 로그는 `evidence/workspace-tests.tap`예요.
- `scripts/browser-smoke-workspace.mjs`: 실제 Chrome 폼으로 등록·의뢰·배정·검토·답변·재문의를 실행했어요. 통신 실패·오래된 입력 충돌 때 내용 보존, 390px 화면·대화창, Tab 이동·Esc 닫기·저장 후 초점 복귀도 검사했어요. 결과는 `evidence/browser-results.json`이에요.
- `scripts/test-legacy-isolated.mjs`: 합성 자료의 별도 서버에서 기존 관리자·이미지·상담 API와 사업계획·상품 상세·상담·장바구니 브라우저 검사 6개가 통과했어요. 인쇄용 사업계획 화면과 모바일 표시도 기존 시험에 포함돼요. 결과는 `evidence/legacy-results.json`이에요.

화면은 [컴퓨터 미리보기](evidence/workspace-desktop.png), [휴대폰 미리보기](evidence/workspace-mobile.png)를 확인하세요. 이 캡처는 실제 고객 자료가 없는 시험 화면이에요.

브라우저 재조회와 SQLite 재개방은 확인했지만 **실제 로그아웃·재로그인은 구현·검수하지 않았어요.** `ACCEPTANCE.csv`의 A01은 로그인 제외 부분 검증으로 남기고, 후속 출시 항목은 미실시로 유지해요. 자료 권한 시험도 실제 인증 시스템을 검증한 결과로 확대하지 않아요.

## 남은 거리

로그인·신원 확인·실제 직원 계정과 관리 범위, 개인정보 정책을 결정한 뒤 신원 공급 경계를 연결해야 해요. 업로드의 악성 파일 정밀 검사와 실제 고객 자료 보유·파기·복구 절차도 운영 접수 전에 갖춰야 해요. 현재의 파일 형식·헤더 검사를 악성 파일 검사로 표시하지 않아요. 기존 접수의 계정 연결·운영 자료 이전은 구현하지 않았어요.

권한 판정과 업무 저장을 분리된 모듈로 만든 이유는 로그인 선택을 미룬 채 핵심 흐름을 시험하되, 개발용 역할 전환이 운영 서버에 섞이지 않게 하기 위해서예요. 별도 서버와 시험 신원은 개발본의 범위이며 최종 인증 구조의 대체물이 아니에요.

운영 소스·데이터·PM2·nginx·DNS·공유 hook·인증서와 외부 연락은 변경하지 않았어요. 배포·push·서비스 재시작은 실행하지 않았어요. 브랜치는 작업 사본을 구분하기 위한 것이며, 기존 미커밋 수정과 섞인 커밋도 만들지 않았어요. 검토용 변경본은 `implementation.patch`로 별도 기록해요. 다음 작업은 로그인 범위 결정 또는 이 개발본 화면 검토이고, 운영 반영은 별도 작업이에요.
