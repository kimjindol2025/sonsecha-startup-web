# 손세차장 첫 출시 구현 지시서 초안

## 착수 해석 관문

시작 전에 이해한 목적지를 한 줄로 남겨 주세요. 목적지는 고객이 본인 후보지를 의뢰하고, 배정된 담당자의 답변을 재로그인 후 확인하는 첫 출시예요. 해석이 다르거나 모호한 부분이 있으면 질문해 주세요. 질문은 미완이 아니라 완성도를 높이는 과정이에요.

Kim의 후속 지시 **“코딩 시작 로그인은 이번에는 패스”**로 구현에 착수했어요. 로그인·본인 확인·실제 직원 계정은 이번 구현에서 제외해요. 운영에 노출하지 않는 별도 작업 사본과 로컬 시험 신원으로 업무 흐름·자료 권한을 검증해요. 실제 로그인 후 재조회 검수는 통과 처리하지 않아요. 배포·운영 자료 변경·서비스 재시작 승인은 포함하지 않아요. 진행 경로와 모듈 구성은 실행자가 근거를 갖고 선택해요.

## 목적지

시험 계정의 고객이 사업·후보지를 저장하고 검토를 의뢰해요. 관리 책임자가 해당 사업을 직원 개인 계정에 배정하고, 담당자가 근거 있는 공개 답변을 남겨요. 고객은 로그아웃·재로그인 후 본인 결과와 과거 이력을 확인해요. 소유권·현재 배정·중복 방지·충돌 처리는 화면뿐 아니라 서버 자료 요청에서 검증해요.

첫 출시에는 계약 점검·매물 의뢰·신규 사업계획 연결·견적·일정·운영 문의를 넣지 않아요. 기존 접수 계정 연결 제외는 사장님 확정이 필요한 제안이에요. 정확한 권한·상태 규칙은 PRD v3 5·7절, 시험 항목은 v3 부록③과 `ACCEPTANCE.csv`를 따라요.

## 금지선

- 운영 서비스 폴더의 기존 수정사항을 되돌리거나 다른 작업과 섞지 않아요. `baseline.json`의 HEAD만으로 작업 사본을 만들면 아직 커밋되지 않은 수정이 빠지므로 파일 해시와 실제 소스 사본도 대조해요. `/tmp` 사본은 임시이므로 없어지면 같은 기준으로 다시 만들고 확인해요.
- 구현은 별도 작업 사본에서 해요. 기존 `data/`, `dist/`, `.dist-before-qa-20261107-112404/`, 백업, 기존 자료·시험 표시는 변경·삭제하지 않아요. 운영 자료를 시험 환경으로 복사하지 않아요.
- PM2·nginx·DNS Manager·Gogs watcher·공유 hook·인증서·전체 실행 관리 설정을 조작하지 않아요. `pm2 restart`, `reload`, `save`를 실행하지 않아요. 운영 서버 재시작이 필요하면 대상과 정확한 작업을 적고 별도 승인을 기다려요.
- 배포 자동화는 이미 있어요. `git push`가 배포로 이어질 수 있으므로 승인 없이 push·배포 webhook 호출·등록 스크립트 실행을 하지 않아요.
- 기존 관리자 세션이나 상담 접근키를 신규 고객·담당자 신원으로 승격하지 않아요. 소유자·역할·배정·행위자는 서버 정본으로 결정해요. 비밀정보·인증번호·접근키·연락처·서류 내용을 로그·문서·git에 남기지 않아요.
- 실제 외부 연락·인증 메시지 발송·제휴·과금·개인정보 이전은 별도 승인 없이 하지 않아요. 시험용 인증 수단을 쓰면 시험 환경으로 한정하고 운영 우회 경로가 되지 않게 해요.
- 이번 구현의 변경 범위는 `workspace-store.mjs`, `workspace-preview.mjs`, `workspace.html`, `src/workspace.js`, `src/workspace.css`, `scripts/test-workspace.mjs`, `scripts/browser-smoke-workspace.mjs`, `scripts/test-legacy-isolated.mjs`, `package.json`, `vite.config.js`, 이 디렉터리의 작업서·검수표·구현 보고·증거예요. 기존 변경사항과 섞어 커밋하지 않아요. `git add -A`와 관련 없는 파일 포함은 금지해요. push는 사용자 확인 후예요.

별도 작업물은 기존 관리자 차단·로컬 상품 사진·모바일 메뉴·파비콘·장바구니·상품명 수정과 그 시험 스크립트예요. 현재 작업 트리의 기존 변경 목록은 `baseline.json`을 기준으로 보존해요. 후속 작업자가 작성한 변경도 함께 확인해요.

## 완료 기준

- 시험 고객 A의 등록·의뢰·배정·답변·재로그인 결과 조회가 연결돼요. 저장 결과와 마지막 저장 시각이 실제 서버 성공과 일치해요.
- 고객 B와 미배정·재배정 이전 담당자로 사업·후보지·첨부의 직접 요청을 보내면 본문·파일·내부 자료가 나오지 않아요. 재배정 확정 뒤 신규 수정도 저장되지 않아요.
- 응답 유실 후 같은 제출을 다시 보내면 접수·메시지·답변·이력이 중복되지 않아요. 같은 식별값의 다른 내용과 오래된 자료 버전은 조용히 덮어쓰지 않아요.
- PRD에 없는 상태 전이는 서버가 거부해요. 상태 변경·공개 답변·내부 메모·재문의는 허용된 역할과 조건에서만 처리돼요. 재문의는 같은 접수번호를 유지해요.
- 후보지 보류·탈락·정정 후에도 제출 당시 자료·근거·공개 답변·첨부 관계를 조회할 수 있어요. 고객 응답·화면·내려받기에 내부 메모가 없어요.
- `ACCEPTANCE.csv`의 첫 출시 항목을 실제로 실행하고 통과·실패·보류와 증거 위치를 남겨요. 후속 출시 항목과 미실시는 통과에 포함하지 않아요.
- 기존 회귀는 격리된 데이터와 브라우저에서 확인해요. 특히 상품 수정·상담 생성 시험을 운영 주소에 보내지 않아요. 휴대폰·키보드·초점 복귀·인쇄는 실제 브라우저 증거가 있어야 해요.
- 변경본과 실제 테스트 명령·출력·실패·남은 결정이 검토 가능하고, 운영 반영 없이 멈춘 상태를 보고해요.

## 보고 양식

“여기까지 왔고, 남은 거리는 이것” 형식으로 보고해 주세요.

결과에는 변경 파일, 실제 실행 명령·시험 주소·데이터 위치, 항목별 실측과 증거, 남은 실패·미실시·dirty 파일, 커밋이 있으면 전체 해시 목록을 적어요. 실행하지 않은 검수는 통과라고 쓰지 않아요.

판단에는 이해한 목적지, 갈림길에서 선택한 방법과 이유, 어려웠던 점, 방향이 다르다고 느낀 부분과 질문, 범위 밖 관찰을 적어요. 추가 구조와 범위 확대가 필요했다면 목적과 비용을 설명해요. push·배포·재시작·외부 발송 여부는 명시해요.
