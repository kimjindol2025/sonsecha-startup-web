# 손세차장 첫 출시 코딩 준비

후속 지시 “코딩 시작 로그인은 이번에는 패스”를 반영한 구현 범위·실행 방법·검증 결과는 `IMPLEMENTATION.md`를 확인해요. 아래 내용은 착수 전 준비 기록이에요.

2026년 11월 7일 한국시간. 기준은 이 대화에서 Kim이 제공한 PRD 개정판 v3예요. 이 문서는 v3의 구현 준비안이며 PRD 원문을 대체하지 않아요. 현재 승인 범위는 소스 분석, 준비 문서와 격리된 기존 기능 검증이에요. 신규 기능 구현·운영 데이터 변경·배포 승인은 포함하지 않아요.

첫 출시의 목적은 **후보지 등록 → 검토 의뢰 → 담당자 답변 → 재로그인 후 본인 결과 확인**이에요. 기존 절차·계산기·상품·인쇄·접수·의견은 유지해요. 기존 접수의 계정 연결 제외는 아직 사장님 확정 전 제안이에요.

## 현재 소스와 차이

| 영역 | 확인한 소스 | 첫 출시에서 필요한 변화 |
| --- | --- | --- |
| 실행 구조 | `package.json`, `server.mjs`, `vite.config.js` | 현재 Node HTTP·Vite·일반 JavaScript 구조를 기준으로 설계해요. 프레임워크 전환은 범위에 없어요. |
| 후보지 저장 | `src/main.js`의 `sonsecha-candidates-v2` | 브라우저 자료와 별도로 계정 소유 사업·후보지의 서버 저장이 필요해요. 기존 로컬 자료를 자동 이전하지 않아요. |
| 기존 상담 | `consultations-store.mjs`, `src/consultations.js` | 현재는 접수번호와 `x-consultation-key`로 인증해요. 이 접근키를 신규 계정의 본인 확인으로 간주하지 않아요. |
| 기존 관리자 | `server.mjs`의 `sessionFor`, `src/admin.js` | 단일 비밀번호와 메모리 세션에는 담당자 신원이 없어요. 신규 검토 업무에는 실명 여부와 별개로 개인별 계정 식별·역할·배정 범위가 필요해요. 기존 관리자 세션에 새 관리 책임자 권한을 자동 부여하지 않아요. |
| 기존 상태 | `consultations-store.mjs`의 `allowedStatuses`, `updateStatus` | 허용 값 확인과 v3 상태 전이 검사는 달라요. 기존 상태를 일괄 치환하지 않고 신규 업무 규칙을 분리해요. |
| 기존 메시지 | 같은 파일의 `addMessage` | 신규 문의에는 메시지별 중복 방지, 공개 답변과 내부 메모 분리, 작성자·변경 이력이 필요해요. |
| 기존 계산·장바구니 | `src/business-plan.js`, `src/main.js` | 첫 출시에는 유지해요. 사업·후보지 연결은 후속 출시예요. |
| 검증 명령 | `package.json`, `scripts/` | `npm test`는 현재 정의돼 있지 않아요. 검증한 명령과 대상 시험 서버를 보고서에 그대로 남겨요. |

위 내용은 소스 분석이에요. 운영 데이터베이스·실제 고객 자료를 읽거나 v3 기능이 이미 구현됐다고 판정한 결과는 아니에요. 현재 변경 파일·HEAD·파일 해시는 `baseline.json`, 이번 격리 검증 결과는 `verification.json`을 확인해요.

## 화면과 업무 경계

고객 화면은 로그인, 사업 목록·상세, 후보지 초안·등록, 의뢰 내용 확인·제출, 접수 상세·공개 답변·추가자료·재문의로 나눠 설계해요. 직원 화면은 개인 로그인, 관리 책임자의 미배정 목록·배정, 담당자의 배정 사업·검토표·공개 답변·내부 메모를 제공해요. 별도 진입점 또는 경로의 최종 이름은 상세 설계에서 정해요.

새 화면과 자료 요청이 기존 상품 관리자 권한을 상속하지 않게 해요. 기존 `src/main.js` 안에 계정·권한·신규 접수 업무를 모두 추가하는 대신 해당 책임을 별도 모듈로 둘 수 있어요. 화면 파일 분리 방식은 실행자 재량이에요.

## 자료와 API 설계 준비안

현재 SQLite 사용 경험을 활용해 **신규 검토 업무 전용 저장소**를 두는 안을 제안해요. 실제 파일 위치와 스키마는 상세 설계에서 확정해요. 기존 `consultations.sqlite`, `feedback.sqlite`, 상품·콘텐츠 JSON을 신규 구조로 바꾸거나 복사하는 마이그레이션은 이번 준비 범위에 없어요.

| 자료 | 관계와 반드시 지킬 조건 |
| --- | --- |
| 계정·세션 | 고객과 직원 모두 서버가 확인한 계정 식별값을 사용해요. 로그인 수단, 세션·만료·복구 정책은 결정 후 설계해요. |
| 사업·배정 | 사업 소유 계정, 현재 담당자, 관리 책임자 범위를 서버가 판정해요. 재배정 이력에는 행위자·시각·사유를 남겨요. |
| 후보지·자료 버전 | 사업에 속하고 초안 저장에는 자료 버전을 사용해요. 제출 당시 버전과 최신 초안을 구분해요. |
| 검토 의뢰 | 사업·후보지 버전·접수번호·상태·버전을 연결해요. 제출 기록은 수정하지 않아요. |
| 검토 항목·공개 답변 | 출처·확인 주체·확인일·재확인 필요 여부를 저장해요. 정정은 이전 기록을 참조하는 새 버전이에요. |
| 메시지·내부 메모 | 재문의는 같은 접수에 메시지를 추가해요. 고객 응답 자료에는 내부 메모를 포함하지 않아요. |
| 제출 처리 기록 | 행위자·사업·작업 종류·식별값·내용 비교값·처리 결과를 연결해요. 계정 소유권을 먼저 검사하고 중복 재시도에는 이미 처리한 번호·결과를 반환해요. 다른 내용이면 충돌이에요. |
| 첨부 | 사업·대상 자료·버전·공개 범위를 연결해요. 공개 정적 파일 경로에서 제공하지 않고 매번 현재 접근 권한을 검사해요. |
| 상태·감사 이력 | 변경 전후·행위자·시각·사유를 추가해요. 접수 생성·답변·상태·중복 방지 기록이 일부만 저장되지 않도록 같은 변경 단위로 처리해요. |

신규 API의 경로 이름은 상세 설계에서 정하되 기존 `/api/consultations` 계약을 변경하지 않는 방향을 제안해요. 모든 신규 자료 요청은 로그인 → 소유·관리 범위·현재 배정 → 자료 버전·상태 전이 → 저장 순으로 검사해야 해요. 계정·소유자·역할·담당자를 요청 본문 값만으로 결정하지 않아요. 세션을 사용하는 쓰기 요청에는 위조 요청 방어도 포함해요.

같은 작업 식별값 재시도는 변경을 다시 실행하지 않아요. 새 답변이나 상태 변경에 오래된 버전이 오면 덮어쓰지 않고 충돌과 최신 상태 확인 경로를 제공해요. 재배정 권한 판정은 실제 저장 시점까지 유효해야 해요. 초안 입력은 충돌 때도 보존해요.

## 결정 시점

| 시점 | 필요한 결정 | 현재 상태 |
| --- | --- | --- |
| 상세 설계 전 | 고객 로그인·본인 확인 수단, 인증 연동 주체 | 사용자 선택 대기. 이메일 인증번호는 비교안이며 채택되지 않았어요. |
| 상세 설계 전 | 직원 개인 계정 방식, 최초 관리 책임자 지정과 관리 범위 | 미정. 기존 공용 관리자 로그인으로 대체하지 않아요. |
| 상세 설계 전 | 첫 출시 범위와 기존 접수 계정 연결 제외 | v3 제안. 사장님 확정 여부를 기록해야 해요. |
| 상세 설계 중 | 열린 직원 화면 권한 재확인·잠금 시점, 첨부 형식·개수·용량·검사 방식, 오류·충돌 표시 | 설계 항목. 서버의 신규 요청 권한 검사는 필수예요. |
| 실제 고객 접수 전 | 개인정보 수집·보유·파기·임시 저장 정책, 운영 담당과 응대 기준 | 미정. 시험 자료로만 검증해요. |
| 운영 반영 전 | 백업·복구·반영 범위, 실제 배포 명령, 재시작이 필요하면 대상 프로세스와 정확한 작업 | 별도 승인 사항이에요. |

인증 공급자·가격·이용조건은 이번 준비에서 조사하거나 확정하지 않았어요. 선택 뒤 해당 공식 자료와 실제 설정을 확인해요. 이메일·문자 발송, 외부 제휴 요청, 과금은 이번 준비에서 실행하지 않아요.

## 구현 순서 제안

1. 로그인·개인별 직원 신원과 첫 출시 범위를 정하고 화면·자료·권한 설계를 확정해요.
2. 신규 저장소, 소유·배정 권한, 후보지 초안 버전 저장을 격리 환경에서 구현해요.
3. 의뢰 생성·중복 방지·배정·상태 전이·공개 답변·재문의·감사 이력을 연결해요.
4. 고객·직원 화면과 첨부 권한을 연결하고 정상·실패 검수표를 실행해요.
5. 기존 기능 회귀와 복구 점검을 마친 변경본·증거를 제시해요. 운영 반영은 별도 승인 후예요.

첫 구현 지시서 초안은 `WORK_ORDER.md`, 검수 대응표는 `ACCEPTANCE.csv`예요. 미결정 선택을 구현자가 임의로 확정하거나 준비 요청을 개발 착수 승인으로 바꾸지 않아요.
