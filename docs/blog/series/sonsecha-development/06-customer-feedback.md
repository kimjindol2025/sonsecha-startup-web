## AI로 빨리 만드는 것과 고객이 쓰는 것은 달랐다

사용자는 유튜브 영상 `AI로 개발하다가 망했습니다 (총 매출 400원)`을 공유했다. 영상의 교훈은 고객을 확인하지 않고 자신의 감, 유료화와 완성도를 기준으로 제품을 만들면 AI로 빠르게 개발해도 실패할 수 있다는 것이었다.

현재 사이트에도 같은 질문이 필요했다. 기능을 더 만드는 것보다 무료 사용자가 어디에서 도움을 받고 어디에서 막히는지 먼저 물어야 했다. 클릭 분석은 행동을 보여주지만 이유는 알려주지 않는다. 그래서 사용자는 “피드백 받게 게시판 우리서버 db”를 요청했다.

## 외부 폼 대신 우리 서버 SQLite

프로젝트에는 외부 DB 패키지가 없었지만 운영 Node 22는 내장 SQLite를 지원했다. 별도 월 비용 없이 `data/feedback.sqlite`를 만들고 다음 정보를 저장했다.

- 도움됐어요·불편해요·기능 제안·기타 의견
- 관련 화면과 의견 본문
- 페이지와 기기 구분
- 새 의견·검토 중·완료 상태
- 작성·수정 시각

이름, 전화번호, 이메일과 IP 컬럼은 만들지 않았다. 공개 작성은 시간당 5개로 제한하고 숨은 입력 필드로 단순 봇을 걸러냈다.

## 방문자 작성창과 관리자 수신함

방문자는 모든 화면의 `의견 보내기` 버튼으로 모바일 모달을 연다. 현재 위치를 기준으로 창업가이드, 12단계, 후보지 체크, 제품몰, 장바구니·견적서를 추천하고 5~1,000자의 의견을 받는다.

관리자는 네 번째 `사용자 피드백` 탭에서 새 의견, 검토 중, 완료와 전체 건수를 본다. 내용·화면 검색과 상태 필터를 사용하고 각 글의 처리 상태를 DB에 저장한다.

“게시판”을 공개 목록으로 만들지 않은 이유도 기록해야 한다. 검수되지 않은 글에는 개인정보, 광고와 악성 내용이 포함될 수 있다. 현재 목적은 커뮤니티가 아니라 고객 반응 수집이므로 관리자 전용 수신함을 기본값으로 정했다.

## 운영 검증

임시 DB에서 정상 작성, 짧은 입력 거절, 스팸 미저장, 관리자 조회와 상태 변경을 확인했다. 390px Chrome에서는 방문자 모달과 관리자 게시판 모두 가로 넘침이 없었다. 운영 배포 후 DB 권한 `0600`, 공개 작성 경로와 인증된 관리자 조회를 확인했고 운영 DB에는 테스트 글을 남기지 않았다.
