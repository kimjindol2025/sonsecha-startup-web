## “모바일 최적화”를 했지만 끝나지 않았다

첫 모바일 작업에서는 860px 이하에서 사라지던 탐색 메뉴를 복원하고, 히어로와 12단계 카드, 버튼, 입력창의 크기를 조정했다. 320px·390px Chrome 화면과 1440px 데스크톱 화면을 확인했고 빌드도 통과했다.

그럼에도 사용자는 운영 화면을 보고 “아직 모바일 최적화 안 됨”, “모바일 기준 가독성 없음”이라고 지적했다. 자동 캡처가 깨지지 않는 것과 사람이 현장에서 편하게 쓰는 것은 다른 기준이었다.

교정 후에는 다음을 명시적으로 고정했다.

- 모바일 헤더를 두 줄 탐색 구조로 유지
- 단계 카드에서 제목과 설명의 실제 폭 확대
- 상세·필터·추가·삭제 버튼을 터치 가능한 높이로 조정
- 입력 글꼴을 16px 이상으로 설정해 iOS 자동 확대 방지
- 긴 조사 본문과 링크의 줄바꿈, 전체 가로 넘침 확인

## 주소마다 체크리스트가 달라야 했다

사용자는 “여기에 주소별 체크리스트 개별 제공?”, “후보지 추가는? 추가버튼”이라고 요청했다. 이 교정으로 저장 구조가 한 후보지 중심에서 여러 후보지 중심으로 바뀌었다.

- 후보지 탭과 `+ 후보지 추가` 버튼
- 후보지 이름·주소·종합 판정
- 주소마다 독립된 12단계 완료 상태
- 상세 체크, 메모, 단계별 가능·조건부·불가 판정 분리
- 후보지 전환·삭제·초기화
- 기존 단일 후보지 데이터의 자동 이전

같은 사업이라도 주소가 다르면 용도지역, 건축물 용도, 하수 연결과 진출입 조건이 달라진다. 주소별 저장 분리는 UI 편의가 아니라 계약 판단 오류를 막기 위한 데이터 경계였다.

## 인터넷 조사를 실무 확인 경로로 바꾸다

사용자는 이어서 각 항목을 인터넷으로 자세히 조사하라고 요청했다. 토지이음, 정부24, 국가법령정보센터, 국세청과 KOSHA 같은 공식 경로를 중심으로 각 단계에 다음 정보를 보강했다.

- 담당 부서에 물어볼 질문
- 제출하거나 확인할 서류
- 단계 완료를 입증할 자료
- 실제 법령·민원 안내 링크

온라인 자료만 보고 허가가 가능하다고 단정하지 않도록 관할 부서의 서면 또는 민원 회신을 최종 근거로 삼는 원칙도 기록했다.
