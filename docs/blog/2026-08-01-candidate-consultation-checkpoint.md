## 사용자 요청을 해석한 방식

사용자는 브라우저에만 저장되던 후보지 체크리스트·메모·사진 중 본인이 선택한 내용만 대한이엔지 관리자에게 보내고, 접수번호를 받은 뒤 관리자 답변을 다시 후보지 기록에 남기는 기능을 요청했다. 이어 상담 페이지 전송은 이메일로 하고 상담 건별 대화방도 만들라고 지시했다.

이를 자동 동기화가 아니라 **사용자가 승인한 시점의 상담용 스냅샷**으로 해석했다. 후보지 원본은 계속 브라우저에 남고, 주소·메모·사진은 각각 선택하지 않으면 서버 요청 데이터에 포함되지 않는다. 접수 뒤의 대화도 후보지 전체를 계속 동기화하지 않고 해당 상담 건에만 누적한다.

## 변경 내용

### 선택·미리보기·동의

- 1단계 후보지 영역에 `상담용 자료 만들기`와 `상태·대화 보기`를 추가했다.
- 주소, 예상 세차장 형태·베이 수, 메모·담당기관 문의 기록, 사진을 개별 선택한다.
- 전송 직전에 실제 공유될 후보지 요약, 단계별 상태, 미확인 항목, 메모, 사진 썸네일과 상담 질문을 보여준다.
- 동의 체크는 자동 선택하지 않으며, 미동의 상태의 전송은 브라우저와 서버 양쪽에서 차단한다.
- 기존 후보지 저장 키 `sonsecha-candidates-v2`와 체크·판정·상세 메모 필드는 유지했다.

### 사진 처리

- 선택 사진은 후보지별 IndexedDB에 보관한다.
- 브라우저 canvas에서 최대 1,600px WebP로 다시 생성해 EXIF 위치정보를 제거한 뒤 전송한다.
- JPG·PNG·WebP, 원본 10MB 이하, 최대 10장으로 제한한다.
- 상담 건을 먼저 만든 뒤 사진을 한 장씩 업로드한다. 일부 사진이 실패해도 접수번호와 질문은 사라지지 않는다.
- 실패 사진은 IndexedDB에 남아 재시도할 수 있다.
- 사용자 대화방과 관리자 상세 양쪽에서 전송된 첨부사진을 삭제할 수 있다.

### 서버 스냅샷과 접근키

- `data/consultations.sqlite`에 상담 건, 처리상태, 공유 스냅샷, 질문, 사용자 확인 여부와 대화를 저장한다.
- 첨부파일은 `data/consultation-uploads/<상담 내부 ID>/`에 저장한다.
- 사용자에게 보이는 접수번호와 별도로 32바이트 접근키를 발급한다.
- 접수번호만 아는 사람은 상담 상태·메시지·사진을 조회할 수 없다.
- 브라우저는 후보지별 `sonsecha-consultations-v1`에 접수번호와 접근키를 저장해 새로고침 후에도 상태를 확인한다.
- 공개 상담 생성은 접속 주소별 시간당 8건으로 제한한다.

### 관리자 검토 요청과 대화방

- 기존 관리자에 `후보지 검토 요청` 메뉴를 추가했다.
- 목록에는 접수번호, 접수일, 후보지명, 주소 공유 여부, 진행률, 미확인 수, 사진 수, 질문과 처리상태를 표시한다.
- 처리상태는 접수, 확인 중, 추가자료 요청, 답변 완료, 상담 연결, 종료다.
- 상세에서는 공유된 기본정보, 단계·세부 체크, 메모, 사진과 대화를 확인한다.
- 관리자는 전체 상담 또는 특정 체크항목을 골라 답변할 수 있다.
- 사용자가 `답변을 후보지 메모에 반영`을 누르면 기존 `detailNotes`를 덮어쓰지 않고 출처·접수번호·답변시각·메시지 ID를 가진 새 `consultationNotes`를 추가한다.
- 같은 관리자 메시지는 ID로 중복 반영을 막는다.
- 대화방 1차 구현은 WebSocket 실시간 채팅이 아니라 서버 저장과 열 때 조회하는 방식이다.

## 이메일 경계

사용자가 이메일 전송을 요청했지만, 후보지명·주소·질문·사진을 이메일 본문이나 첨부에 복제하지 않았다. 이메일은 접수 알림과 인증된 관리자 화면 진입 용도로만 사용할 예정이다.

현재 정확한 수신주소가 아직 지정되지 않아 상담 건의 이메일 상태는 `발송 대기`로 저장된다. 다음 작업에서 수신주소와 “접수번호 + 관리자 로그인 링크만 전송” 범위를 승인받은 뒤 기존 Alert Hub에 연결해야 한다. 상담 접수와 대화 기능 자체는 이메일 설정이 없어도 동작한다.

## 실수와 교정

- 처음 이메일을 곧바로 외부 알림에 연결하려 했지만 정확한 수신처와 메일에 포함할 식별정보 범위가 정해지지 않았다. 기능 완성을 서두르면 사용자가 선택한 서버 스냅샷보다 통제하기 어려운 이메일 사본이 생길 수 있었다. 외부 발송은 멈추고 `queued` 상태와 개인정보 없는 알림 원칙만 코드에 남겼다.
- 실제 브라우저 테스트에서 사용자가 대화에 첨부한 스크린샷을 사진 테스트에 쓰려 했다. 그 특정 이미지의 전송 승인은 없었으므로 사용하지 않고, 공개 디자인 라이브러리의 비민감 PNG로 사진 경로만 검증했다.
- 첫 Chrome 대화방 검증은 화면 전환 중 DOM이 아직 생기기 전에 읽어 실패했다. 비동기 재렌더 구간의 일시적인 요소 부재를 허용하도록 대기 루프를 고친 뒤 전체 흐름을 다시 통과했다.
- 정적 빌드 결과를 서버가 즉시 제공하는 구조라 서버 재시작 전에는 새 화면과 이전 API가 잠시 어긋날 수 있다. 이후 작업에서는 서버 코드와 정적 화면의 반영 순서를 먼저 계획해야 한다.

## 구현 언어와 회수 조건

기존 서비스가 Node HTTP 서버, Node 내장 SQLite, Vite 브라우저 모듈과 하나의 관리자 인증 흐름으로 운영되고 있어 이번 기능도 같은 서버에 최소 확장했다. 이는 기존 서비스 변경 위험과 바이너리 사진·인증 해시 결합을 줄이기 위한 브리지 선택이다.

FreeLang/AFJ가 바이너리 업로드, SQLite 트랜잭션, 접근키 해시 검증과 Alert Hub 연동을 안정적으로 지원하면 상담 저장소와 API를 AFJ로 회수하고, 브라우저 선택·미리보기 어댑터만 JavaScript에 남기는 것이 다음 언어 과제다.

## 후속 교정 · 12부 전체와 복수 후보지 비교 접수

### 사용자가 바로잡은 범위

첫 구현과 안내는 현재 선택된 후보지 한 곳을 전송하는 구조였고, 화면 맥락상 1부 후보지 사전 확인만 상담하는 것처럼 읽혔다. 사용자는 검토요청서가 **1부만이 아니라 1~12부 전체 기록**을 다루고, 후보지도 `1번 단독`, `1·2번`, `1·2·3번 전체`처럼 선택할 수 있어야 한다고 바로잡았다.

이 교정은 화면에 체크박스를 추가하는 것으로 끝나지 않는다. 한 접수번호로 비교하더라도 각 후보지의 체크·판정·메모·사진·관리자 답변이 섞이면 기록의 증명력이 사라진다. 따라서 접수는 하나로 묶고 사실 기록은 후보지 ID로 끝까지 분리했다.

### 변경한 구조

- `후보지 검토 요청서` 고정 버튼을 기존 `의견 보내기` 바로 위에 추가했다.
- 요청서 첫 화면에서 현재 후보지 1곳을 기본 선택하고, 후보지 개별 선택과 전체 선택을 제공한다.
- 선택된 후보지는 한 접수번호 아래 `snapshot.version: 2`의 `candidates[]`로 저장한다.
- 후보지마다 `candidateRef`, 12단계 상태, 세부 체크, 메모, 주소, 예상 형태, 사진 공유 여부를 별도로 보존한다.
- 선택되지 않은 후보지 ID가 전송 목록과 스냅샷에 섞이면 서버가 요청을 거부한다.
- 사진 업로드 전에 어느 후보지 자료인지 지정한다. 첨부 테이블에 `candidate_ref`를 추가하고 후보지별 10장 제한·재시도를 적용한다.
- 같은 접수번호를 선택된 각 후보지의 로컬 상담 목록에 연결하고, 선택하지 않은 후보지에는 기록하지 않는다.
- 관리자 상세는 후보지별 카드 안에 12단계·세부 체크·메모·사진을 분리한다.
- 개별 답변 context를 `후보지 ID:체크 ID`로 저장해 답변을 해당 후보지 메모에만 추가한다.
- 기존 단일 접수 `version: 1`도 계속 읽고, 기존 저장 키와 후보지 체크 데이터 구조는 변경하지 않았다.

### 후속 검증과 운영 반영

- 임시 SQLite API 스모크에서 기존 단일 접수 호환, A+B 묶음 접수, C 제외, 후보지별 12단계·메모·사진, 관리자 항목 답변 연결을 통과했다.
- 실제 Chrome에서 A+B를 선택하고 C를 제외한 뒤 B 사진을 전송했다. A/B에는 같은 접수번호가 저장되고 C에는 접수 기록이 없음을 확인했다.
- 관리자 화면에는 A/B 카드만 나타났으며 A 항목 답변을 A 메모에 반영해도 B 메모는 변하지 않았다.
- 새로고침 후 선택·접수·메모가 유지됐고 모바일 390px에서 문서와 모달의 가로 넘침이 없었다.
- kim의 명시 승인 후 운영 빌드와 PM2 `sonsecha-startup-web` 프로세스 하나만 재시작했다.
- 공개 페이지, 새 JS·CSS 자산과 관리자 페이지가 모두 HTTP 200으로 응답했고 재시작 로그에는 SQLite 실험 기능 경고 외 런타임 오류가 없었다.

### 다음 Codex가 반복하지 말아야 할 실수

- “후보지 화면에 있는 상담 버튼”을 “1부만 상담”으로 축소 해석하지 않는다. 검토요청의 정본 단위는 후보지별 12부 전체 기록이다.
- 복수 후보지를 한 건으로 묶더라도 배열을 평탄화하지 않는다. 후보지 ID 경계를 사진·답변·메모 반영까지 유지한다.
- 운영 서버가 `dist`를 직접 제공하므로 서버 형식이 바뀌는 작업은 정적 빌드와 해당 PM2 단일 프로세스 재시작을 연속 수행한다.
- 이메일은 아직 `queued` 상태다. 실제 수신주소와 알림 페이로드 승인 전에는 발송 완료라고 기록하지 않는다.

### 사용자가 보여준 증거

운영 반영 뒤 사용자가 요청서 첫 화면 스크린샷을 제시하며 “변화가 없어 보인다”고 지적했다. 지적이 맞았다. 단계별 메모를 서버 스냅샷, 다음 미리보기와 관리자 상세에 연결했지만 사용자가 실제로 공유를 결정하는 첫 화면에는 여전히 `1~12단계 메모·담당기관 문의 기록` 체크박스 한 줄만 보였다.

스크린샷의 현재 후보지는 주소 미입력, 12단계 0/12, 작성 메모 0개였다. 표시할 실제 메모가 없다는 사실과 별개로, 어떤 12단계 기록이 요청서에 들어가고 메모 공유 선택에 따라 무엇이 달라지는지는 첫 화면에서 확인할 수 있어야 했다.

### 가시성 개선

- 공유 선택 바로 아래에 `1~12단계 기록 확인` 영역을 추가했다.
- 선택 후보지별로 12단계 판정과 각 단계의 저장 메모 본문을 요청서 전송 전에 펼쳐 본다.
- 메모가 없는 단계에는 `작성된 메모 없음`을 표시해 빈 기록과 화면 누락을 구분한다.
- 메모 공유 전에는 `메모 공유 선택 필요`와 후보지별 `메모 제외`를 표시한다.
- 사용자가 메모 공유를 직접 체크하면 `메모 N개 요청서 포함`과 `전송 포함`으로 즉시 바뀐다.
- 후보지를 단독·복수·전체로 바꾸면 단계 기록과 메모 수도 선택 후보지 기준으로 다시 계산한다.
- 메모는 담당기관 답변 등 민감정보가 될 수 있으므로 자동 체크하지 않는다. 사용자가 내용과 포함 여부를 같은 화면에서 보고 승인하는 원칙을 유지한다.

### 검증과 남은 운영 경계

- 실제 Chrome에서 A+B 후보지를 선택한 뒤 첫 화면에 후보지 기록 카드 2개, A의 실제 메모 문구와 공유 전·후 상태 문구가 나타나는지 확인했다.
- 이후 미리보기, 사진, 관리자 요청서, A 항목 답변, A 메모 반영, B 비혼합, 새로고침과 모바일 390px 흐름도 함께 통과했다.
- API 스모크는 메모의 단계 번호 보존과 기존 메모 ID에서 단계 복원을 통과했다.
- 이번 첫 화면 가시성 개선은 소스와 임시 빌드에서 검증했으며 아직 운영 정적 파일에는 반영하지 않았다. 추가 서버 변경은 없으므로 운영 반영 시 PM2 재시작은 필요하지 않다.

### 교훈

데이터가 서버에 존재한다는 사실만으로 사용자가 기능 변화를 확인할 수 있는 것은 아니다. 사용자가 결정을 내리는 화면에서 실제 전달될 기록과 제외 상태를 보여줘야 동의가 의미를 가진다. 다음 작업에서는 내부 데이터 경로 검증과 함께 첫 화면의 시각적 증거를 완료 조건으로 둔다.
