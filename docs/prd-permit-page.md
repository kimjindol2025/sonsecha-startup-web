- 문서 경로: `docs/prd-permit-page.md`
- 문서 상태: 개발 검토용 초안
- 기준일: 2026-11-09 (한국시간)
- 대상 프로젝트: `sonsecha-startup-web`
- 신규 기능 가칭: `/permit`
- 출처: [손세차장 허가 확인 페이지 기획서 v1](https://app.notion.com/p/412858c4cfed817d98e0c8e0d5846e4a), [손세차장 땅찾기·허가·견적 기획서 v3](https://app.notion.com/p/412858c4cfed813fb8d7c86ea31fc624)

## 태그와 문서 읽는 법

- `[운영자 결정 필요]`: 운영자에게 정책·사업 범위·문구·책임 범위를 확인받기 전에는 확정하지 않는다.
- `[고객 화면]`: 고객에게 질문하거나 화면에 표시할 내용이다.
- `[개발자 결정]`: 구현 방식, 상태 관리, 접근성, 오류 처리 등 개발자가 설계·검증할 내용이다.
- `[현재 구현]`: 현재 저장소와 운영 코드에서 확인한 사실이다.
- `[신규 제안]`: `/permit`에 추가할 요구사항이며 아직 구현되지 않았다.

법령과 행정 절차는 법률 자문이나 허가 확정이 아니다. 화면의 모든 판정에는 “최종 확인은 관할 기관”을 표시한다.

## 1. 문서 상태·목적·대상 독자

### 1.1 문서 목적

이 문서는 기존 창업가이드에 허가 확인 전용 페이지를 추가할 때 필요한 제품·데이터·검수 기준을 정의한다. Notion 원문에 있는 사업 제안과 현재 사이트의 구현 사실을 분리해, 개발자가 바로 화면·저장·판정·테스트 범위를 판단할 수 있게 하는 것이 목적이다.

- `[현재 구현]` 이 문서는 운영 사이트 변경이나 배포 승인이 아니다. 현재 저장소에는 `/permit` 라우트가 없다.
- `[신규 제안]` 허가 확인은 “허가를 자동으로 받거나 확정하는 기능”이 아니라, 고객이 자료를 모으고 관할 기관에 물어볼 질문을 정리하는 준비 도구로 만든다.
- `[운영자 결정 필요]` 페이지 공개 시점, 메뉴 노출 위치, 최종 안내 문구, 상담 전환 방식은 운영자 승인을 받은 뒤 확정한다.

### 1.2 대상 독자

| 독자 | 이 문서에서 확인할 것 |
| --- | --- |
| 운영자 | 실제 제공 범위, 고객에게 약속할 수 있는 문구, 상담·공사·전문가 연결 정책 |
| 고객 화면 기획자/디자이너 | 질문 순서, 결과 상태, 근거·주의 문구, 기존 화면과의 연결 |
| 개발자 | 라우트, 데이터 모델, localStorage 호환, 판정 우선순위, API·보안·테스트 |
| QA/운영 검수자 | 현재 기능과 신규 기능의 회귀 범위, 수용 기준, 법령 시점 경고 |

## 2. 문제 정의와 목표

### 2.1 문제

- 기존 후보지 체크리스트는 주소별 온라인·현장·관할 부서 확인을 기록할 수 있지만, 허가에 필요한 건축물 용도·용도지역·폐수·하수 조건을 독립적인 질문 흐름으로 정리하지 않는다.
- 고객이 “세차장이 가능한가”를 묻더라도 현재 앱은 자료 확인과 판정을 기록하는 도구이지, 주소별 법적 가능성을 자동 확정하는 서비스가 아니다.
- Notion 원문은 1단계 허가 확인과 2단계 공사 준비를 분리하지만, 현재 `/construction-prep`는 구현되지 않았다.
- 법령·조례·하수 수용·배출 성분·기존 허가 승계는 주소와 시점에 따라 달라져, 일반 규칙을 고객의 허가 완료로 표시하면 오인 위험이 있다.

### 2.2 목표

- `[고객 화면]` 후보지별 주소·공간·건축물대장·용도지역·폐수·하수·기존 영업 여부를 순서대로 입력할 수 있게 한다.
- `[고객 화면]` 모름·미확인·근거 없음은 정상 입력 상태로 허용하고, 가능으로 자동 변환하지 않는다.
- `[고객 화면]` 확인된 사실, 고객 추정, 기관 회신, 확인일·출처를 구분해 보여준다.
- `[개발자 결정]` 일차 상태는 `가능(검토 여지) / 확인 필요 / 어려움` 세 상태로 제공하되, 법적 허가·신고 완료·공사 착수 승인으로 해석되지 않게 한다.
- `[운영자 결정 필요]` 결과에서 “공사 준비하기”, “허가 상담 먼저 하기”, 전화 상담 중 어떤 행동을 제공할지 확정한다.

### 2.3 성공 기준

- 고객이 후보지 하나의 허가 확인 자료와 미확인 질문을 출력·보관할 수 있다.
- 주소를 바꿨을 때 이전 후보지 자료가 새 주소에 재사용되지 않는다.
- 근거와 확인일 없는 입력이 가능 상태를 만들지 않는다.
- 기존 `#top`, 후보지 체크리스트, `#plan`, `#shop`, 상담·이메일·관리자 기능이 회귀하지 않는다.

## 3. 현재 서비스와 신규 `/permit` 경계

### 3.1 현재 구현 사실

| 영역 | 현재 구현 | `/permit`과의 관계 |
| --- | --- | --- |
| `#top` 창업가이드 | 12단계 로드맵, 단계별 설명·체크, 밝은 후보지 체크리스트 | 기존 자료·상태를 유지하고 `/permit` 진입점을 별도 추가할 수 있다. |
| 후보지 체크·판정·메모 | `sonsecha-candidates-v2` localStorage에 후보지별 `stepChecks`, `stepStatuses`, `detailChecks`, `detailNotes`, `detailStatuses` 등을 저장한다. | `[개발자 결정]` 신규 페이지는 기존 후보지 객체를 직접 확장할지 별도 `permit` 네임스페이스를 둘지 결정해야 한다. 아래 원칙은 기존 데이터 손상을 막기 위해 별도 하위 객체를 권장한다. |
| `#plan` 사업계획서 | 사업계획·비용·매출 가정 기능이 별도 모듈로 동작한다. | 허가 판정을 매출·입지 점수·견적 계산이 상쇄하지 않게 분리한다. |
| `#shop` 제품몰 | 공개 상품 목록·상세·장바구니·공개 상품 API, 관리자 상품 관리가 있다. | 허가 결과에 제품 구매를 자동 추천하거나 판매 기능을 끼워 넣지 않는다. |
| 상담 | 후보지 검토 요청서, 후보지별 자료 선택·미리보기·동의·전송 및 상담 상태 조회가 있다. | `/permit`의 요약을 상담 자료에 포함할지, 사용자가 선택할지 운영 정책을 확인한다. |
| 의견·이메일 | `/api/feedback` 의견 보내기와 상담 관련 서버 이메일 발송이 구현되어 있다. SMTP 설정이 없으면 명확한 오류를 반환한다. | `/permit`에서 자동 발송하지 않고, 기존 상담·이메일 동작을 재사용할지 별도 결정한다. |
| 관리자 | 관리자 인증·상품·콘텐츠·문의·상담 관리 API와 화면이 있다. | 허가 자료를 관리자 서버에서 자동 열람·수정하는 기능은 이번 범위가 아니다. |
| `/construction-prep` | 현재 미구현. | 링크를 만들지 말고 “공사 준비 기능 준비 중” 또는 상담·요약 내려받기를 보여준다. `[운영자 결정 필요]` |

### 3.2 신규 `/permit`의 경계

`/permit`은 다음을 담당한다.

1. 후보지 식별과 고객 입력
2. 건축물대장·용도지역·폐수·하수·기존 영업 조건의 수동 기록
3. 출처·확인일·기관 회신 기록
4. 일차 분류와 미확인 질문 목록
5. 요약 내려받기·인쇄·기존 상담 연결

다음은 담당하지 않는다.

- 로그인·서버 계정·직원 원격 열람 `[신규 제안]`
- 공공자료 자동 조회·주소 자동 전송 `[신규 제안]`
- 허가·신고 신청 대행, 법률 자문, 기관 답변 위조
- 매물 중개·계약·결제
- 공사비 자동 산출·확정 견적
- 개인 서류 원본·주민번호·계약서의 기본 수집
- 미구현 `/construction-prep`를 숨은 진행판으로 대체 공개

## 4. 사용자 역할 구분(운영자/고객/개발자)

| 역할 | 책임과 권한 | 화면·문구 태그 |
| --- | --- | --- |
| 운영자 | 제공할 상담·공사·전문가 연결 범위, 책임 제한, 법령 근거 갱신 주기, 고객 자료 수신·보관 정책을 결정한다. | `[운영자 결정 필요]` |
| 고객 | 후보지 주소·자료·추정·기관 회신을 직접 입력하고, 결과를 참고용으로 확인한다. | `[고객 화면]` |
| 개발자 | 라우팅·상태 모델·입력 검증·이스케이프·저장 실패·접근성·회귀 테스트를 구현한다. 정책을 임의로 확정하지 않는다. | `[개발자 결정]` |

운영자와 개발자는 고객 입력을 기관 인증 결과처럼 표현하지 않는다. 고객이 작성한 “담당 부서 답변”은 고객 기록이며, 기관 시스템과 연동된 회신이 아니다.

## 6. 고객에게 실제로 묻는 질문과 입력 필드

원문 기준으로 허가 확인 질문을 공사 준비 질문보다 먼저 묻는다. 모든 질문에는 `모름/확인 필요`를 허용한다.

| 순서 | 고객 질문 | 입력 필드 | 저장·검증 원칙 | 태그 |
| --- | --- | --- | --- | --- |
| 시작 | 어디에서 어떤 세차장을 준비하나요? | 후보지 별칭, 주소·지번, 희망 지역, 셀프/손세차/자동 | 주소와 별칭은 후보지 식별용. 자동 주소 조회는 기본 제공하지 않는다. | `[고객 화면]` |

입력 제약:

- `[개발자 결정]` 텍스트 길이·숫자 범위·단위 변환·음수·문자 입력을 검증한다.
- `[개발자 결정]` 사용자 입력은 HTML에 `innerHTML`로 삽입하지 않고 텍스트 노드·속성 대입 또는 이스케이프를 사용한다.
- `[개발자 결정]` 1㎥=1,000L 변환 시 원 단위와 원 입력값을 보존한다.
- `[개발자 결정]` 주소·이름·메모·기관 회신을 URL query string, 분석 이벤트, 오류 로그에 넣지 않는다.
- `[운영자 결정 필요]` 연락처·이메일을 `/permit`에서 직접 받을지, 기존 상담 화면에서만 받을지 결정한다.

## 7. 사용자 흐름과 화면 목록

### 7.1 흐름

`진입 → 후보지 선택/새로 시작 → 공간·형태 입력 → 허가 질문 → 근거·확인일 기록 → 일차 결과 → 미확인 질문·기관 확인 목록 → 요약/인쇄 → 상담 또는 공사 준비 안내`

- `[고객 화면]` 한 번에 한 질문 묶음을 보여주고 뒤로 가도 입력을 유지한다.
- `[고객 화면]` 저장 상태와 “이 기기에만 저장” 안내를 항상 표시한다.
- `[개발자 결정]` 후보지 주소·대장 용도·용도지역·폐수 조건이 변경되면 기존 결과를 과거 기록으로 보존하고 현재 결과를 `재확인 필요`로 표시한다.
- `[운영자 결정 필요]` 결과에서 공사 준비 화면으로 넘어가는 조건과 버튼 문구를 확정한다.

## 8. 판정 규칙(가능/확인 필요/어려움)과 금지된 자동 판단

### 8.1 표시 상태

| 상태 | 의미 | 고객 문구 | 태그 |
| --- | --- | --- | --- |
| 가능 | 필요한 건물·지역·폐수 근거와 기관 확인 기록이 있고 해결되지 않은 장애가 없는 상태 | “확인된 기록상 검토 여지가 있습니다. 최종 확인은 관할 기관입니다.” | `[고객 화면]` |
| 확인 필요 | 핵심 값·근거·기관 회신 중 하나 이상이 비어 있거나 충돌하는 상태 | “아직 확인하지 못한 조건이 있습니다. 관할 기관에 확인할 질문을 정리했습니다.” | `[고객 화면]` |
| 어려움 | 우수관 직방류 계획, 배출 경로 불명·처리계획 부재, 운영자 승인된 보수 기준 등 먼저 보완해야 할 장애가 있는 상태 | “이 조건은 먼저 기관 확인·계획 보완이 필요합니다.” | `[운영자 결정 필요]` |

### 8.2 우선순위

`어려움` 장애가 있으면 어려움 → 장애는 없지만 하나라도 미확인이면 확인 필요 → 세 축의 근거와 기관 확인 기록이 모두 있으면 가능(검토 여지) 순서로 한다.

- `[개발자 결정]` 점수·매출·상품 구매 여부가 허가 상태를 상쇄하지 않는다.
- `[개발자 결정]` 모름·빈칸·조회 실패·오래된 기관 회신은 가능으로 바꾸지 않는다.
- `[개발자 결정]` 서로 충돌하는 기관 회신은 확인 필요로 돌리고 재확인 질문을 만든다.
- `[운영자 결정 필요]` 특정 용도지역·기존 건물·폐수 조건을 “어려움”으로 분류하는 세부 규칙은 법령 최신 확인과 운영 승인 후 등록한다.

### 8.3 금지된 자동 판단

- 허가 완료, 신고 완료, 영업 가능, 공사 착수 승인으로 표시하지 않는다.
- “상업지역이면 가능”, “하수관이 있으면 적법”, “폐수 없음이면 제외”, “100㎡ 미만이면 허가 면제”로 자동 결론 내리지 않는다.
- 물 사용량을 폐수량으로 자동 간주하지 않는다.
- 고객이 입력한 담당자·기관 회신을 기관 인증 데이터로 승격하지 않는다.
- 점수·매출·경쟁점·제품 구매 의사로 허가 위험을 상쇄하지 않는다.
- 법령 문구만으로 특정 주소의 결과를 확정하지 않는다.

모든 결과에는 “이 결과는 자료 정리를 위한 일차 안내이며 법률 자문이나 허가 확정이 아닙니다. 최종 확인은 관할 기관에 하세요.”를 포함한다.

## 9. 데이터 모델 및 기존 후보지 localStorage 연동 원칙

### 9.1 현재 후보지 저장 사실

- `[현재 구현]` 저장 키는 `sonsecha-candidates-v2`이며 후보지별로 `id`, 이름, 주소, 종합 상태, 단계 체크·판정, 세부 체크, `detailNotes`, `detailStatuses`, 상담 메모 등이 저장된다.
- `[현재 구현]` 후보지 전환 시 현재 후보지의 체크·메모·판정이 분리되어 복원된다.
- `[현재 구현]` 기존 `#top` 현장 확인 8개 항목은 세부 체크·메모·`가능/보류/미판정` 상태를 저장한다.

### 9.2 `/permit` 권장 모델

기존 후보지 객체의 기존 필드를 덮어쓰지 않고 다음처럼 하위 객체를 추가한다.

```js
candidate.permit = {
  schemaVersion: 1,
  updatedAt: 'ISO-8601',
  answers: {
    spaceType: 'warehouse|factory|parking|retail|existing-wash|other|vacant|unknown',
    washType: 'self|hand|automatic|unknown',
    buildingUse: { value: '', confidence: 'confirmed|estimated|unknown', checkedAt: '', source: '' },
    address: { value: '', checkedAt: '', source: '' },
    landUse: { value: '', checkedAt: '', source: '' },
    wastewater: { route: 'public-sewer|rainwater|private|outsourced|other|unknown', note: '' },
    existingBusiness: { value: 'new|transfer|lease|continue|unknown', evidence: '' },
    waterUse: { value: null, unit: 'L|m3|unknown', basis: 'measured|equipment|estimate|unknown' },
    wastewaterVolume: { value: null, unit: 'L|m3|unknown', source: '' },
    authorityRecords: [],
  },
  evidence: [],
  status: 'unreviewed|possible|needs-confirmation|difficult',
  statusReason: '',
  rulesVersion: '',
  history: [],
};
```

- `[개발자 결정]` 실제 필드명·열거값은 구현 전에 스키마 리뷰를 거친다.
- `[개발자 결정]` 기존 `detailNotes`와 신규 `permit.answers`를 자동 병합하거나 기존 메모를 삭제하지 않는다.
- `[개발자 결정]` 기존 후보지 데이터가 없거나 손상되면 새 `permit`만 기본값으로 만들고 기존 후보지·상품·관리자 데이터는 건드리지 않는다.
- `[개발자 결정]` 서버 저장·로그인·직원 공유를 추가하려면 별도 PRD와 개인정보·권한 검토를 먼저 한다.
- `[운영자 결정 필요]` 기존 후보지 현장 체크 항목을 `/permit` 결과에 복사해 보여줄지, 링크로만 연결할지 결정한다.

## 10. 근거·법령·확인일 관리

- `[고객 화면]` 각 핵심 입력에는 출처 URL, 자료 기준일, 고객 확인일, 확인 주체, 기관 분야·회신 요지를 기록할 수 있어야 한다.
- `[고객 화면]` 근거가 없는 추정값은 `추정`으로 표시하고, 미확인 값은 `미확인`으로 표시한다.
- `[개발자 결정]` 법령 카드에는 법령명·조문·링크·확인일·규칙 버전을 함께 표시한다.
- `[운영자 결정 필요]` 법령·공식 링크의 검토 주기와 책임자를 지정한다.
- `[개발자 결정]` 2015년 법제처 해석, 과거 개정본, 지역별 안내문은 현행 전국 규칙처럼 표시하지 않는다.
- `[고객 화면]` 토지이음·정부24·세움터·인터넷등기소 등 외부 링크는 고객이 직접 열람하며, `/permit`이 주소를 자동 전송한다고 표시하지 않는다.
- `[개발자 결정]` 출처 링크가 죽거나 자료 시점이 오래되면 `재확인 필요`를 표시하고 가능 판정을 만들지 않는다.

법령 관련 화면 문구는 법률 자문이 아니며, 개별 주소의 최종 확인은 관할 건축·도시계획·환경·하수 담당 기관에 요청한다.

## 11. 개인정보·보안·저장 범위

### 11.1 기본 저장 범위

- `[신규 제안]` 최초 버전은 로그인 없이 기기 localStorage에 저장한다.
- `[개발자 결정]` 이름·연락처·주민번호·계약서·등기부 원본·건축물대장 원본·사진 업로드는 기본 수집하지 않는다.
- `[고객 화면]` “이 기기에만 저장되며 브라우저 자료 삭제 시 사라질 수 있습니다. 필요한 자료는 내려받아 보관하세요.”를 표시한다.
- `[개발자 결정]` localStorage는 암호화 금고가 아니므로 같은 브라우저·기기 이용자가 접근할 수 있다는 한계를 안내한다.
- `[개발자 결정]` 저장 실패·용량 초과·두 창 충돌 시 조용히 덮어쓰지 않고 실패와 복구 방법을 표시한다.

### 11.2 전송과 출력

- `[개발자 결정]` 입력값을 분석 이벤트·오류 로그·URL·외부 검색 요청에 넣지 않는다.
- `[고객 화면]` 상담 전송은 사용자가 공유 항목과 동의를 명시적으로 선택한 뒤에만 실행한다.
- `[운영자 결정 필요]` 상담 요청 시 주소·허가 질문·메모·기관 회신을 포함할지 항목별로 결정한다.
- `[개발자 결정]` 내려받기·인쇄에는 판정 이유·미확인 항목·근거·확인일·주의 문구를 포함한다.
- `[개발자 결정]` 서버 이메일 SMTP 비밀값을 브라우저·문서·로그에 노출하지 않는다.

## 12. 개발 범위와 제외 범위

### 12.1 포함 범위

- `/permit` 직접 접속과 기존 `#top`에서의 선택적 진입
- 후보지 선택·새 후보지·질문 단계·뒤로 가기·기기 저장
- 건물·용도지역·폐수·하수·기존 영업 조건 수동 입력
- 근거·확인일·기관 회신·메모 기록
- 세 상태 일차 분류, 미확인 질문, 요약·인쇄
- 기존 후보지·상담과의 명시적 연결
- 키보드 접근성·모바일 반응형·입력 검증·XSS 방지

### 12.2 제외 범위

- 공공자료 자동 조회·지도·자동 주소 검색·매물 수집
- 법적 허가·신고 자동 판정, 신청 대행, 공식 기관 인증
- 로그인·서버 저장·담당자 배정·고객 계정
- `/construction-prep` 실제 화면 구현
- 공사비·장비비·창업 총액의 자동 확정 견적
- 매물 중개·계약·결제·전문가 소개료 처리
- 주민번호·신분증·계약서·등기부 원본 업로드
- 운영자 승인 전 법령 규칙을 확정 문구로 공개
